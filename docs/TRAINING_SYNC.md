# Структурированный журнал и автоматическая синхронизация

После входа FitLife автоматически синхронизирует журнал через Backend. Каждое изменение сначала сохраняется локально; сеть и аккаунт не обязательны для тренировки. Экран «Аккаунт и синхронизация» показывает состояние, повтор и расхождения версий. Создание и восстановление серверных архивов заменены работой с отдельными записями. Файловый импорт/экспорт `.fitlife` остаётся самостоятельной функцией.

## Состав данных

| Запись | Сохраняемые данные |
| --- | --- |
| `workout` | UUID и название; даты начала/окончания; active/paused/completed/cancelled; отдых и его срок; текущая и завершённые паузы; накопленное время пауз; заметка; явно записанный вес тела; признак неизвестной длительности |
| Упражнения и подходы | Исходные UUID и порядок; исторические имя, группа мышц и инструкция упражнения; повторы, кг, разминка, время выполнения, множитель нагрузки, заметка; суперсеты; каждый этап дропсета и его выполнение |
| `template` | Все упражнения и индивидуальные цели подходов; отдых; базовый вариант и именованные вариации; группы, мышцы и области мышц; дни расписания |
| `bodyWeight` | UUID, дата, кг и необязательный workout UUID; замер может пережить удаление тренировки |
| `heartRate` | Workout UUID, версия, режим appleHealth/bluetooth, необязательный origin liveHealthKit, упорядоченные измерения с точными датами и дробным BPM |

Нормализованные таблицы Backend содержат корневые записи, упражнения, подходы, дроп-этапы, паузы, вариации и измерения пульса. Только небольшие наборы выбора мышц/дней хранятся списками JSON. Новые записи не создают `Backups.Payload`. UUID упражнений каталога индексируются; исторические названия не меняются вслед за каталогом.

Даты контракта — числовые Unix seconds, включая дробную часть. Вес хранится в кг. Сервер повторно проверяет правила действующего Core; неизвестные поля не отбрасываются молча. Отсутствующее значение и пустой список сохраняют различие там, где это допускает Core.

Питание, сон, фотографии, настройки и credentials не входят в этот контракт. Лицензированный каталог упражнений и изображения продолжают работать офлайн. Файловый архив строго `com.fitlife.archive` v4 по-прежнему не содержит пульс; серверная синхронизация передаёт сохранённый пульс отдельно. Новых запросов разрешений HealthKit для синхронизации нет.

## HTTP-контракт

Оба маршрута требуют JWT с допустимым `sub`, audience `fitlife-api` и действующей сессии через introspection Authentication. Владелец берётся только из токена, клиент не передаёт owner ID. Лимит — 240 запросов в минуту на владельца; прикладные OAuth scopes не добавлены.

`GET /v1/training/changes?after=0&limit=50` возвращает:

```json
{
  "changes": [
    {
      "kind": "bodyWeight",
      "id": "00000000-0000-0000-0000-000000000001",
      "revision": 1,
      "deleted": false,
      "value": {
        "id": "00000000-0000-0000-0000-000000000001",
        "measuredAt": 1700000000.125,
        "weightKG": 75.25,
        "workoutID": null
      }
    }
  ],
  "cursor": 1,
  "hasMore": false
}
```

Это лента **последних версий** агрегатов, а не история всех промежуточных изменений. Версии монотонны в пределах владельца; записи и tombstones упорядочены по версии. `limit` — от 1 до 100; страница также ограничена объёмом данных. Получатель продолжает с возвращённого `cursor`, пока `hasMore` равно true. Чтение графа выполняется в согласованном снимке PostgreSQL.

`POST /v1/training/changes` принимает массив от 1 до 100 мутаций:

```json
[
  {
    "kind": "bodyWeight",
    "id": "00000000-0000-0000-0000-000000000001",
    "baseRevision": 1,
    "deleted": true,
    "value": null
  }
]
```

Ответ — массив подтверждённых `TrainingChange` в порядке запроса. `baseRevision: 0` означает новую запись; для правки/удаления передаётся последняя известная версия. Один пакет атомарен: ошибка поздней записи откатывает предыдущие графы и счётчик версий. PostgreSQL advisory lock сериализует запись и удаление одного аккаунта. Повтор того же канонического значения идемпотентен, даже если предыдущий ответ потерян.

Ошибки: 400 — невалидные данные/курсор; 401 — требуется вход; 403 `account_deleted`; 409 `training_conflict` с `current`, `workout_missing`, `training_limit` либо `cursor_reset_required`; 413 — превышен размер; 415 — неверный Content-Type; 429 — частота. При недоступной introspection доступ закрыт с 503.

Пакет и каноническое значение одной записи ограничены 30 MiB; клиент проверяет ответ до 32 MiB с учётом оболочки. До 10 000 живых записей каждого типа, кроме 1 000 планов; всего до 100 000 метаданных, включая tombstones. До 10 000 измерений пульса на тренировку. Эти ограничения не являются общей квотой диска для открытой регистрации аккаунтов.

Правка тренировки сохраняет её пульс. Удаление тренировки удаляет связанный граф пульса и создаёт отдельное уведомление об удалении; взвешивания сохраняются. Удаление аккаунта очищает структурированные данные и прежние архивы под той же блокировкой. Существующий внутренний маршрут `/internal/users/{uuid}/backups` сохранён, его действие охватывает весь журнал.

## Работа клиента

`WorkoutWorkspaceRepository` уведомляет об успешных личных записях, импорт Watch/файла и App Intents используют тот же путь. Пульс уведомляет только после успешной файловой записи. Отправка объединяет близкие изменения с задержкой 2 секунды. Foreground, восстановление сети и явный повтор также запускают сверку. В фоне сетевой координатор останавливается; постоянное фоновое исполнение не обещается.

`TrainingSyncCoordinator` сначала получает изменения, затем отправляет локальные отличия и снова читает ленту. Устойчивые baselines и курсор в защищённых файлах позволяют найти правки и удаления после перезапуска, даже если callback не доставлен. Подтверждение относится к отправленному снимку: новая правка во время запроса остаётся ожидающей отправки. После каждого await актуальное локальное значение проверяется заново; пульс записывается сравнением и заменой внутри actor.

Одновременные отличающиеся правки не перезаписываются автоматически. Экран показывает локальную и серверную версии, включая удаление, и требует явного выбора с подтверждением. Предпросмотр привязан к серверной версии и локальному хешу; устаревший выбор отклоняется. Для удаления тренировки проверяется также показанная запись пульса. Конфликт одной записи не блокирует остальные; конфликт тренировки удерживает связанный пульс. Другую активную тренировку нельзя принять, пока не завершена текущая.

Если сервер восстановлен из более ранней БД, клиент сбрасывает серверные версии, сохраняя сведения о локальных удалениях. Старые серверные записи не воскрешаются без выбора пользователя. Повреждённый файл состояния не заменяется пустым состоянием.

При настроенном Backend основной SwiftData store открывается без CloudKit, переключатель iCloud для тренировок скрыт. Два механизма не синхронизируют один журнал одновременно. Без серверной конфигурации прежний необязательный режим CloudKit сохраняется.

## Аккаунты и Apple Watch

Первый вошедший аккаунт однократно принимает существующий локальный журнал. Последующие аккаунты имеют отдельные локальные namespaces из issuer и UUID пользователя; чужой журнал автоматически не загружается в новый аккаунт. Namespace и переназначение SwiftData записей меняются одной транзакцией без новых колонок. Питание и сон остаются локальными данными устройства.

Выход останавливает обмен и сохраняет выбранный журнал на устройстве. Сохранённые журналы можно открывать офлайн; для обмена нужен соответствующий аккаунт. Смена журнала во время тренировки блокируется. Перед сменой завершаются сетевые операции и записи датчика. Файлы пульса первого аккаунта копируются с устойчивой отметкой завершения; повтор не восстанавливает уже удалённый пульс.

Watch сохраняет принадлежность активной тренировки и каждой записи outbox. Контекст текущего/первого аккаунта передаётся через WCSession. Локальный текущий Watch archive v1 явно мигрирует в v2 с сохранением UUID и очереди; это не поддержка прежних продуктовых архивов. iPhone не подтверждает запись другого аккаунта, и часы сохраняют её до открытия соответствующего журнала. Удаление из outbox по-прежнему происходит только после подтверждения успешного локального сохранения на iPhone. Обновите приложения и на телефоне, и на часах.

## Обновление сервера

1. Сохраните обычную резервную копию Backend-БД и постоянных ключей.
2. Сохраните фактические имена БД/ролей, пароли, PFX и bind mounts в существующей `.env`. Новых переменных, OAuth clients или Apple identifiers для этой функции нет. Значения `BACKEND_DB_NAME=fitnesstracker_backend` и `BACKEND_DB_USER=fitnesstracker_backend` можно оставить, если это рабочие имена.
3. После получения кода выполните `docker compose up -d --build`. Backend до открытия HTTP применит `20261112194506_CreateTrainingModel` и однократно перенесёт **последний полный текущий v4 архив** каждого ещё не перенесённого владельца. Предыдущая миграция идентификатора применяется раньше. Для отдельного запуска без HTTP доступен `docker compose run --rm backend --migrate`.
4. Проверьте логи и `/health`, затем обновите iPhone/Watch и войдите в аккаунт. Сохранённый на телефоне пульс отправится с клиентом: в прежних серверных архивах его не было.

Перенос сохраняет исходные `Backups`, UUID и поля; не объединяет старые полные снимки, чтобы не вернуть ранее удалённые записи. После переноса повторный startup и новые вручную созданные архивы не восстанавливаются поверх правок журнала. Обновите все устройства перед продолжением тренировок: старый клиент пишет только архивы и не участвует в change feed. Повреждённый checksum, невалидные доменные данные или последний архив неподдерживаемой версии прерывают startup, откатывая перенос этого владельца и сохраняя исходник. Уже завершённые переносы других владельцев не откатываются. Версии v1–v3 не преобразуются в v4; при таком отказе нужны проверка/актуальный экспорт, а не удаление БД.

Маршруты `/v1/backups` сохранены для доступа к существующим архивам и действующего серверного контракта; новый iOS-клиент ими не пользуется. Администратору по-прежнему нужны резервные копии всей PostgreSQL-БД: синхронизация распространяет и удаления. Данные передаются по HTTPS, но не имеют end-to-end шифрования от администратора вашего сервера.

## Проверки

Серверные тесты написаны на **C# / xUnit** в `Tests/Server`. `TrainingValidationTests` проверяет 149 допустимых и ошибочных границ; HTTP-наборы проверяют JSON/пакеты/курсоры, потоковые лимиты, отмену и атомарность. PostgreSQL-наборы проверяют настоящие каскады, квоты, блокировки, согласованное чтение и откат при SQL-ошибке. [Состав наборов](SERVER.md#проверки).

`scripts/check-linux.sh` запускает Core, переносимые OAuth/account/coordinator/файловые проверки, проверяет воспроизводимость `Tests/Server/Fixtures/training-contract.json` настоящим Core, ресурсы, RU/EN, syntax parser и strict lint. Дополнительно Python-генератор воспроизводит `training-validation.json`, а настоящий Core независимо проверяет все 149 ожидаемых результатов C#-тестов. Это защита от расхождения контрактов двух языков; серверные тесты выполняются отдельно через .NET. Apple SDK, SwiftData macro expansion, SwiftUI UI и реальный WCSession на Linux не проверяются.

`scripts/check-server.sh` с `FITLIFE_TEST_POSTGRES` проверяет миграции, перенос, нормализованный round-trip, конкурентные правки/удаление, owner isolation, rollback и HTTP. Для обратной проверки Core задайте `FITLIFE_TEST_TRAINING_PAGE` путём временного JSON при запуске PostgreSQL-категории, затем выполните собранный `training-contract-checks --verify-server <путь>`. Тестовые базы случайные и удаляются после проверки; рабочая БД не используется.

Быстрый запуск только C#-тестов журнала после сборки:

```bash
dotnet test Tests/Server/FitLife.Server.Tests.csproj --no-build --no-restore -m:1 --filter '(FullyQualifiedName~Training)&(Category!=PostgreSQL)'
# С заданным FITLIFE_TEST_POSTGRES к одноразовому PostgreSQL:
dotnet test Tests/Server/FitLife.Server.Tests.csproj --no-build --no-restore -m:1 --filter '(FullyQualifiedName~Training)&(Category=PostgreSQL)'
```
