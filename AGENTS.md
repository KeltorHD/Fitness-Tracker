## 2. Стек и продуктовые ограничения

- Swift 6, строгая проверка concurrency.
- SwiftUI, **iOS 26+**, **watchOS 26+**.
- Нативный Apple Liquid Glass.
- SwiftData, UserDefaults для настроек, Keychain для секретов при необходимости.
- HealthKit, CloudKit, ActivityKit, WidgetKit, App Intents, WatchConnectivity и UserNotifications.
- Swift Package Manager для независимого Core; XcodeGen для структуры Xcode-проекта.
- Swift Testing для Core, XCTest для Apple unit/UI tests.
- URLSession — основной выбор для нового HTTP-клиента, если он понадобится.

Серверный стек: **.NET 10 / C# 14**, ASP.NET Core, EF Core + Npgsql/PostgreSQL. Authentication использует ASP.NET Core Identity + OpenIddict; Backend проверяет JWT и пока отвечает только за резервные копии. Серверные тесты — xUnit, логирование — стандартный `ILogger<T>`, форматирование — `dotnet format`. Конфигурация и команды — в `docs/SERVER.md` и разделах 22/25.

Не понижай deployment target до iOS 17: текущий проект использует API iOS 26. macOS 14 в Package.swift относится к независимому Core, а не к SwiftUI-приложению.

Все функции приложения бесплатны. Не возвращай Pro, paywall, покупки, подписки или StoreKit без нового явного требования пользователя. Основной интерфейс — на русском языке.

Название продукта — FitnessTracker. Прежние storage/wire identifiers в AppCompatibility, legacy archive IDs и aliases Config/Base.xcconfig сохраняются только для совместимости установленных данных; не переименовывай их без явной миграции. Правила — в docs/RENAME.md.

## 5. Архитектура

В Swift-части сохраняй два уровня:

1. **Cross-platform Core:** модели тренировок, упражнений и подходов, шаблоны, валидация, state machine, статистика, календарь, библиотека упражнений, протоколы репозиториев.
2. **Apple layer:** SwiftUI, SwiftData, capabilities и платформенные интеграции.

Core не должен импортировать Apple-only фреймворки или зависеть от SwiftUI/UIKit. Используй `#if canImport(...)` только там, где действительно нужен общий исходник; не скрывай весь Apple-слой ради зелёной Linux-сборки.

MVVM — предпочтительный способ организации новой presentation logic. Существующие `@Observable @MainActor AppStore` и DI через initializer — рабочая основа. Не переписывай приложение и не вводи отдельный ViewModel для каждого маленького View без конкретной пользы.

Authentication и Backend — самостоятельные исполняемые .NET-проекты без ссылок друг на друга и без общей рабочей БД. Authentication владеет пользователями, привязками и токенами; Backend — резервными копиями. Между ними используются OAuth/OIDC, discovery/JWKS и документированный внутренний HTTP-контракт. Не вводи дополнительные слои, общую библиотеку или универсальный repository без конкретной необходимости.

## 6. SwiftUI Views

- Views отвечают за отображение и пользовательские действия.
- Не размещай в них сетевые запросы, запись в SwiftData и сложные доменные расчёты.
- Сложные преобразования данных выноси в Core или presentation model.
- Делай Views небольшими и композиционными; извлекай повторяемые элементы.
- Используй NavigationStack, @State, @Binding, @Environment, .task и ContentUnavailableView по назначению.
- Предусматривай загрузку, пустое состояние, ошибку и успешный результат там, где это требуется.
- Избегай AnyView, ненужного GeometryReader, фиксированных размеров экрана и deprecated API.
- Не добавляй UIKit wrapper, если задачу решает нативный SwiftUI. Точечные UIKit-вызовы для локальных изображений и idle timer уже используются по назначению.

## 7. Presentation models и DI

- UI-состояние изолируй MainActor; предпочитай @Observable.
- Presentation models координируют действия и асинхронные операции, но не становятся универсальными контейнерами всей логики.
- Предпочитай initializer-based DI.
- Вводи протоколы ради тестирования, замены реализации или отделения внешнего сервиса, а не для каждого класса.
- Не добавляй глобальные изменяемые singleton-объекты.
- Существующий FitnessTrackerRuntime обеспечивает один AppStore/ModelContext в app process, включая холодный запуск LiveActivityIntent. Сохраняй это поведение; не создавай конкурирующий context из intent или View.

## 8. Swift coding standards

- Предпочитай struct и let, когда reference semantics и изменение не нужны.
- Используй guard для раннего выхода и описательные имена.
- Выбирай access control осознанно; не делай API public без необходимости.
- Не используй try! или implicitly unwrapped optionals в production-коде без исключительной причины.
- Избегай force unwrap. Существующие константные UUID не являются поводом для несвязанной массовой правки; в новом коде обосновывай исключения.
- Не подавляй warnings и concurrency diagnostics без устранения причины.
- Удаляй неиспользуемые импорты, временный и мёртвый код.
- Следуй существующему форматированию swift format; отступ Swift-кода — два пробела.

## 9. Concurrency

- Используй async/await и structured concurrency.
- Для независимых параллельных операций при необходимости используй TaskGroup.
- Учитывай cancellation и завершай управляемые задачи при потере актуальности.
- Не блокируй main thread.
- Не применяй Task.detached без документированной причины.
- Не добавляй @unchecked Sendable без доказанной безопасности.
- Unstructured Task допустим, если понятны владелец, срок жизни и порядок завершения.
- Через границы actors передавай Sendable value types, Data и безопасные идентификаторы; не передавай ModelContext и SwiftData-модели.
- В callbacks WCSession учитывай выполнение вне main actor; UI и persistence переключай на MainActor.

## 10. Networking и offline

Новая HTTP-интеграция должна использовать отдельный URLSession-сервис с DI, типизированными моделями, проверкой status codes, обработкой decoding/HTTP errors, отменой и тайм-аутами.

Не храни API secrets в коде и не логируй credentials или личные данные.

Текущая библиотека упражнений работает полностью offline. Не заменяй локальный каталог и фотографии обязательным API-запросом или hotlinking. Скачивание материалов в скриптах — отдельная явно запускаемая операция; обычная генерация и unit tests не требуют сети.

## 11. Persistence и совместимость

- SwiftData — для структурированных данных приложения.
- UserDefaults — для небольших настроек и минимальной сводки виджета после opt-in.

- Сохраняй совместимость Codable payloads и стабильность UUID упражнений/тренировок.
- При изменении формата данных предусматривай явную миграцию; не удаляй store как способ исправить ошибку.
- Для CloudKit-compatible StoredRecord сохраняй defaults полей и учитывай ограничения CloudKit. Не добавляй unique constraints без проверки совместимости.
- Не запускай собственную дублирующую синхронизацию поверх SwiftData/CloudKit без обоснования.
- Не заменяй ошибку открытия пользовательского хранилища молчаливым переходом на пустую in-memory базу.

## 12. Правила данных тренировки

- Вес хранится в кг; фунты — преобразование на границе UI.
- Ноль означает отсутствие добавленного веса.
- Выполнение подхода, пауза, продолжение, завершение и отмена проходят через бизнес-правила Core.
- Не изменяй завершённую тренировку через обход валидации.
- Повтор тренировки создаёт новые session/row/set IDs и сбрасывает completion/паузы, сохраняя identity упражнений.
- Рабочий объём исключает разминку и невыполненные подходы.
- Calendar calculations учитывают locale, timezone, границы недели и DST; не считай каждый календарный день равным 86400 секундам.
- Не подставляй вымышленные калории, пульс, вес тела, замеры или числа из референсных скриншотов.

## 13. Live Activities, фон и Watch

- Таймеры опираются на сохранённые даты и интервалы пауз.
- Для Live Activity используй системные SwiftUI timers, а не бесконечный polling процесса.
- Не обещай постоянное выполнение произвольного кода в фоне.
- BackgroundTaskLease предоставляет ограниченное время завершения обновлений; expiration handler должен отменить работу и освободить task.
- Не создавай Live Activity произвольно из background; сохраняй ограничения ActivityKit и настройки пользователя.
- LiveActivityIntent сохраняет изменения и ожидает необходимые updates до возврата из perform().
- FITNESS_TRACKER_APP определён только для главного app target; shared intents не должны открывать SwiftData из widget extension.
- Повторные и устаревшие действия должны быть безопасны: pause/resume идемпотентны, старый skip-rest не сбрасывает новый отдых.
- Watch outbox удаляет запись только после подтверждения успешного сохранения на iPhone. Повторная доставка не создаёт дубликаты.

Делай небольшие осмысленные коммиты по завершении частей работы, как просил пользователь. В коммит включай только относящиеся к задаче изменения. Не утверждай, что push состоялся, если команда завершилась ошибкой; используй полученное разрешение на push в согласованном объёме.

## 25. Серверная разработка на .NET

Эти правила относятся к `Authentication/`, `Backend/`, `Tests/Server/`, серверным конфигурациям и скриптам. Они дополняют общие требования репозитория и не меняют стек iOS/watchOS. Наличие новых соглашений не требует массовой правки прежнего кода.

### C# и документация

- Новые явные private-поля именуй `_camelCase`, private-константы — `ALL_UPPER_SNAKE_CASE`; public-типы, методы и свойства — `PascalCase`.
- Для новых async-методов используй суффикс `Async`, описательные имена с глаголом и `CancellationToken cancellationToken` последним параметром. Framework overrides и публичные контракты сохраняй совместимыми; не переименовывай существующий API только ради стиля.
- Primary constructors уже используются в сервисах, DbContext и контроллерах; сохраняй их для простой DI. Обычный конструктор уместен для проверок и дополнительной инициализации. Не переписывай все конструкторы под один стиль.
- Используй `var`, когда тип очевиден из правой части; явный тип — когда он помогает понять контракт. В реализации выбирай конкретные коллекции, на границах — `IReadOnlyList<T>`/`IReadOnlyCollection<T>` и другие интерфейсы при реальной необходимости.
- Nullable включён. Предпочитай `is null`/`is not null`, безопасную инициализацию и `[]` для пустых коллекций. `null!` допустим только при обоснованной поздней инициализации, например EF navigation property; не маскируй им ошибки контракта.
- На новые собственные классы, методы и public-члены, включая тестовые, добавляй XML-документацию на русском: назначение, значимые условия и результат. Сгенерированные EF-файлы не редактируй ради комментариев.
- C# — 4 пробела; JSON/YAML — 2. Соблюдай применимый `.editorconfig`, если он появится, и сохраняй формат существующих файлов. Fluent-цепочки в новом многострочном коде оформляй по одному вызову на строку с отступом от источника.
- Не добавляй общие `BaseEntity`, `Result`-обёртки, обязательные `#region`, snake_case mapping или новые папки Requests/Responses/Dto, если конкретная задача не требует этого.

### DI, async и внешние зависимости

- Передавай зависимости через конструктор и стандартный ASP.NET Core DI. Отделяй HTTP/persistence от бизнес-правил; не добавляй скрытое изменяемое состояние, глобальные сервисы и service locator в прикладную логику.
- Интерфейсы вводи для полезной границы или замены зависимости. Для тестирования internal-кода при необходимости используй `InternalsVisibleTo`, а не лишние public-методы.
- Используй async/await для ввода-вывода. Не применяй `.Result`, `.Wait()`, `async void` и `Task.Run` для обхода async API. Передавай отмену в EF Core, HTTP, streams и асинхронные итераторы; не превращай отмену в обычную ошибку 500.
- Соблюдай scoped lifetime DbContext. Не передавай его singleton-сервисам и не выполняй параллельные операции на одном экземпляре. При независимых операциях используй отдельные scopes/contexts только при обоснованной необходимости.
- Для исходящего HTTP используй typed `HttpClient`/`IHttpClientFactory`, тайм-ауты, отмену и проверку статуса. Часы передавай через `TimeProvider`, если время влияет на проверяемое поведение.
- Версии SDK задаёт `global.json`, общие свойства — `Directory.Build.props`, версии NuGet — текущие `.csproj`; сохраняй `packages.lock.json` и locked restore. Центрального `Directory.Packages.props`, AsyncFixer, NUnit/Moq и NLog здесь нет. Не добавляй их без отдельной причины и не отключай nullable, warnings as errors или NuGet audit ради прохождения проверок.

### HTTP, аутентификация и резервные копии

- Сохраняй действующие явные маршруты `/connect/*`, `/callback/login/*`, `/v1/account`, `/v1/backups` и внутренний контракт удаления. Не заменяй их маршрутизацией по именам контроллеров/actions. Изменения DTO, status codes, scopes и OpenAPI согласовывай с iOS-клиентом и `docs/SERVER.md`.
- Backend использует minimal API, Auth — MVC/Razor для браузерного входа и аккаунта. Сохраняй эти решения; API-контроллеры при необходимости используют `ControllerBase`, HTML/Razor-контроллеры — `Controller`.
- Контроллеры должны быть тонкими: HTTP binding/атрибуты, маппинг входных и выходных моделей через Mapster, вызов сервиса и формирование HTTP-результата. Бизнес-проверки, Identity/OpenIddict orchestration, запросы EF Core, транзакции, отзыв сессий и удаление данных размещай в сервисах. Не переноси тело контроллера в сервис, возвращающий MVC `IActionResult`: сервис возвращает данные или типизированное решение, HTTP-преобразование остаётся на границе MVC.
- Mapster настраивай явно через отдельный DI `TypeAdapterConfig`, без изменяемого `GlobalSettings`. Маппинг не должен подменять проверку прав, назначать user ID из входного DTO или публиковать EF entities, password hashes, SecurityStamp и ключевой материал. Сохраняй штатные payloads OpenIddict/WebAuthn.
- Возвращай типизированные DTO и подходящие `IResult`/`ActionResult<T>`/`IActionResult`. Не сериализуй EF entities, токены внешних провайдеров и внутренние исключения напрямую. Ошибки оформляй через принятые error codes/ProblemDetails с безопасным сообщением.
- OAuth/OIDC, проверка внешних провайдеров, PKCE S256, ротация и отзыв остаются в Identity/OpenIddict. Не вводи собственный параллельный протокол токенов. Пользователи с одинаковым email не объединяются автоматически; привязка требует явного подтверждённого действия пользователя.
- Auth подтверждает личность и управляет сессиями; разрешения функций Backend определяет сам Backend, без прикладных OAuth scopes. Сохраняй только стандартные scopes протокола входа (`openid`, `profile`, `offline_access`). Backend проверяет подпись JWT, issuer, audience, срок, тип и допустимый `sub`, затем применяет собственные правила доступа и лимиты. Доступ к каждой копии ограничивается `sub`, а не owner ID из тела/URL клиента; scopes в старых токенах не дают дополнительных прав. Внутренний service endpoint не публикуется через внешний proxy.
- Перед каждым доступом к копиям Backend проверяет отзыв через стандартную introspection OpenIddict с отдельным confidential secret, после локальной проверки JWT/прав/rate limit. Не кешируй положительный статус и не продолжай доступ при отказе Auth: revoked даёт 401, недоступный Auth — 503. Выход отзывает всю текущую authorization family, сохраняя другие сессии; Backend не читает Auth-БД напрямую.
- Сохраняй лимиты размера/числа копий, проверку envelope/SHA-256, неизменяемость и идемпотентность PUT. Проверка квоты и удаление аккаунта должны оставаться безопасными при конкурентных запросах. Архив и UUID сохраняют совместимость со Swift Core.
- Серверные копии создаются по явному действию пользователя; они не заменяют локальный журнал и не запускают собственную синхронизацию поверх SwiftData/CloudKit. Email-вход и расширение Backend за пределы бэкапов требуют соответствующей продуктовой задачи.

### EF Core и миграции

- `AuthDbContext` и `BackupDbContext` обслуживают раздельные рабочие базы. Не читай таблицы другого сервиса напрямую. Используй параметризованные запросы, ограниченные выборки и `AsNoTracking` для чтения, если tracking не нужен.
- Группируй взаимозависимые изменения в транзакцию; учитывай ограничения PostgreSQL, уникальность external login и конкурентные загрузки. Не держи открытую транзакцию во время внешнего HTTP-запроса без конкретной причины.
- Миграции находятся в `Authentication/Migrations/` и `Backend/Migrations/`; design-time factories принадлежат соответствующим проектам. Не меняй имена таблиц/полей, ключи и существующие mappings только ради стиля.
- Миграции создаёт и ведёт агент самостоятельно в рамках согласованной задачи: при изменении EF-модели добавляй соответствующую миграцию и обновляй model snapshot штатными инструментами EF Core. Проверяй полученный diff, сохранность данных и применение миграций на изолированной PostgreSQL-БД. Не удаляй и не переписывай уже применённые миграции без отдельного поручения. Дополнительное подтверждение на генерацию миграции не требуется; рабочую БД меняй только в явно разрешённом пользователем объёме.
- По требованию пользователя Authentication и Backend автоматически применяют включённые EF-миграции при обычном запуске, до приёма HTTP-запросов; Auth затем создаёт/обновляет регистрации clients. При ошибке инициализации запуск должен завершаться ошибкой. Сохраняй идемпотентность и блокировки при конкурентном старте. `--migrate` остаётся отдельным режимом применения миграций без запуска HTTP. Это разрешение относится к поведению сервисов: агент не запускает миграции на рабочем сервере без отдельного поручения. Изолированные тестовые БД разрешены.
- Не используй `EnsureDeleted`, удаление volumes или сброс данных как исправление ошибки. `EnsureCreated` допустим для одноразовых SQLite fixtures; он не заменяет проверку PostgreSQL-миграций.

### Серверные тесты

- Используй существующий xUnit-проект `Tests/Server/FitnessTracker.Server.Tests.csproj`. Не создавай по отдельному тестовому проекту на каждый класс и не меняй framework ради соглашений другого репозитория.
- Для нового значимого поведения добавляй содержательные тесты; при исправлении ошибки — регрессионный сценарий. Проверяй happy path, ошибки и границы, отмену, валидацию, сериализацию и значимые defaults. Не ограничивайся проверками присваивания свойств.
- Unit-тесты изолируй через DI и fakes: без реальной сети, внешних секретов, фиксированных задержек и зависимости от порядка запуска. Не добавляй mock-библиотеку, если достаточно простой подмены.
- HTTP/Identity-тесты используют `WebApplicationFactory` и SQLite fixtures; они проверяют статусы, тела и побочные эффекты через реальные компоненты. Не выдавай их за проверку настоящего PostgreSQL, DNS/TLS или входа в Google/Apple/Яндекс.
- PostgreSQL-сценарии помечай `[Trait("Category", "PostgreSQL")]`. Текущий контракт запуска — явный `FITNESS_TRACKER_TEST_POSTGRES` к одноразовому экземпляру и отдельная случайная БД теста; CI поднимает контейнер. Не используй рабочие БД и не скрывай недоступную инфраструктуру успешным результатом или молчаливым пропуском.
- При добавлении контейнерной фикстуры используй закреплённый образ, свободный порт и проверку готовности с тайм-аутом. Не вводи обязательный Testcontainers-пакет и не переписывай действующий способ запуска без конкретной пользы.
- Проверяй реальные контракты: OAuth/PKCE/refresh/revoke, запрет доступа к чужой копии, HTTP/JSON-ошибки, сохранение данных при отказе, повтор PUT, конкурентную квоту и удаление аккаунта. SQLite не заменяет PostgreSQL для миграций и блокировок.
- В многошаговых интеграционных тестах явно разделяй Arrange/Act/Assert и кратко поясняй этапы по-русски. Для коротких очевидных сценариев комментарии необязательны. Описания и условия запуска обновляй в `docs/SERVER.md`.
- Изолируй БД, данные и статическое состояние; при общей изменяемой конфигурации ограничивай параллелизм и восстанавливай её после теста. Освобождай подключения, контейнеры, временные файлы и дочерние процессы также при сбое или отмене.
- После изменения серверного кода выполняй релевантные сборку, функциональные и интеграционные проверки из раздела 22. Отдельно указывай, какие сценарии выполнены и какие требуют Docker, provider registrations или развёрнутого HTTPS-сервера. Для правок только документации достаточно проверки содержания, путей и `git diff --check`.

### Конфигурация и логирование

- Внешний HTTPS обслуживает существующий Nginx на хосте, сертификаты TLS настраивает пользователь. Compose публикует HTTP-порты сервисов только на `127.0.0.1`; не добавляй контейнерный reverse proxy или автоматическую выдачу TLS-сертификатов. PFX для Identity/OpenIddict и Data Protection — отдельные серверные ключи, не сертификаты Nginx.
- Используй стандартную ASP.NET Core configuration: `appsettings.json`, настройки среды, переменные окружения и явно переданные параметры запуска. Вложенные env keys задавай через `__`; не добавляй конфигурационный слой в БД без отдельного требования.
- `.env.example` и безопасные defaults — в репозитории; `.env`, `.local/`, пароли БД, OAuth secrets, PFX/P8 и приватные ключи — вне git. Не отключай в production HTTPS, проверку JWT или antiforgery ради удобства локальной разработки.
- В документации, тестах, примерах и tracked defaults используй домены `example.com` и его поддомены. Реальные адреса развёртывания задавай через игнорируемые `.env` и `Config/Local.xcconfig`; не включай их в коммиты. Для iOS Associated Domains используй локально переопределяемый `FITNESS_TRACKER_AUTH_DOMAIN`.
- Production использует постоянные сертификаты подписи/шифрования и защищённые Data Protection keys; ephemeral credentials допустимы только в тестах, development certificates — в Development. Сохраняй рабочие БД/volumes/ключи и учитывай ротацию при изменении конфигурации.
- Backend хранит собственный постоянный Data Protection key ring, зашифрованный отдельным PFX; ключи Auth в него не монтируются. Не заменяй защиту временным provider и не отключай поддержку шифрования при ошибке зависимости: исправляй runtime-образ или конфигурацию. Подготовка отдельного Backend PFX через `scripts/setup-backend-keys.py` сохраняет существующие ключи и пароли.
- При новом развёртывании постоянные данные серверов хранятся bind mounts в `.local/` рядом с проектом; пути БД, Data Protection keys и token certificates переопределяются в `.env`. Инфраструктуру Backend называй `backend` (БД, пользователь, сервис, настройки, папки); `backups` остаётся названием функции/архивов и её API. При переходе со старых volumes/имён не запускай сервисы на пустом хранилище вместо переноса данных и ключей.
- Используй `ILogger<T>` и структурированные сообщения. Не логируй credentials, Authorization headers, OAuth codes, callback query strings, archive payloads и health data; не включай EF sensitive data logging в production.
- Обновляй `compose.yml`, Dockerfile, `.env.example`, серверные скрипты и `docs/SERVER.md` согласованно с изменениями конфигурации. Проверка Compose config не подтверждает сборку Docker images, миграцию рабочей БД или реальный provider flow.
