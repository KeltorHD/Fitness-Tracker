# FitLife Backend

Самостоятельный ASP.NET Core Backend приложения. Сервер хранит нормализованные тренировки, упражнения, подходы, паузы, планы, замеры веса и пульс. Приложение автоматически синхронизирует записи через `/v1/training/changes`, сохраняя локальную работу офлайн. Последний текущий v4 архив каждого аккаунта переносится при startup; оригиналы сохраняются. [Контракт и обновление](../docs/TRAINING_SYNC.md). Сервер проверяет access JWT Auth Server и отзыв сессии, определяет права локально без прикладных OAuth scopes и изолирует данные по `sub`. БД и пользователь по умолчанию называются `backend`, контейнер PostgreSQL — `backend-db`; данные лежат в `.local/backend-db` или по пути из `.env`.

[HTTP-контракт, лимиты, развёртывание и тесты](../docs/SERVER.md). Пользователи и внешние входы принадлежат проекту Authentication; пароли и refresh tokens в Backend не хранятся.

Обычные диагностические сообщения видны в Docker logs без дополнительных настроек:

```bash
docker compose logs --since=10m -f backend
```

При запуске выводятся подключение к БД, ожидание startup lock, список отсутствующих миграций, завершение миграций/импорта и готовность HTTP. Запросы содержат метод, шаблон маршрута, статус и длительность; успешный `/health` не засоряет журнал. Токены, query, UUID записей, headers и содержимое архива/тренировки не записываются. Console использует UTC timestamps; общий порог остаётся Warning, собственные категории Backend и hosting lifetime — Information. После получения обновления пересоберите сервис: `docker compose up -d --build --no-deps backend`.

Опциональный публичный каталог питания `GET /v1/foods/search?q=...` проксирует perek.us с серверным ключом `FoodSearch:PerekApiKey`. Поиск не требует аккаунта; личные дневники на сервер не передаются. Ключ в iOS не включается. Настройка, ограничения и проверка: [FOOD_SEARCH.md](../docs/FOOD_SEARCH.md).
